# 校园二手交易平台后端核心代码分析

> 本文档基于后端压缩包中的实际代码整理，围绕 `Spring Boot + MyBatis + MySQL` 的三层架构，结合 JWT 认证、AOP、分页拦截、权限控制等机制，对核心模块进行说明。  
> 适合直接作为课程设计、实验报告或项目说明文档的后端部分。

---

## 1. 项目后端总体架构

本项目后端采用经典的三层架构：

```text
Controller 层  →  Service 层  →  Mapper 层  →  MySQL 数据库
```

### 1.1 各层职责

| 层级 | 职责 | 典型代码 |
|------|------|----------|
| Controller 层 | 接收前端请求、解析参数、返回统一响应 | `UserController`、`ProductController` |
| Service 层 | 编写核心业务逻辑，完成校验、组装、状态流转 | `UserServiceImpl`、`OrdersServiceImpl` |
| Mapper 层 | 与数据库交互，执行增删改查 | `UserMapper`、`ProductMapper` |
| 数据库层 | 存储用户、商品、订单、消息、评论等业务数据 | MySQL |

### 1.2 项目采用的关键技术
- **Spring Boot**：提供整体框架与自动配置能力。
- **MyBatis**：用于持久层操作，便于编写复杂 SQL。
- **JWT**：用于用户登录认证和身份识别。
- **AOP**：实现分页参数处理、接口权限校验、操作日志记录。
- **ThreadLocal**：在一次请求过程中保存当前用户信息。
- **RESTful 风格接口**：前端以统一的 HTTP 方法访问后端资源。
- **统一响应封装**：使用 `Result`、`ApiResult`、`PageResult` 统一返回格式。

---
## 2. 项目目录与模块划分
从代码结构看，后端按功能拆分为以下模块：

- **用户模块**：登录、注册、认证、修改密码、后台管理。
- **商品模块**：商品发布、修改、查询、统计。
- **订单模块**：下单、退款、订单查询、卖家订单列表。
- **互动模块**：浏览、收藏、想要、收藏列表、浏览记录。
- **评论模块**：评论新增、修改、查询、删除、点赞状态处理。
- **消息模块**：系统通知、互动提醒、消息已读。
- **分类模块**：商品分类维护。
- **仪表盘模块**：系统统计、商品上架统计。
- **操作日志模块**：记录管理员或用户关键操作。
- **文件模块**：图片/视频上传与资源获取。

这种拆分方式使每个模块的业务边界清晰，便于扩展与维护。

## 3. 通用基础能力设计

## 3.1 统一响应封装

项目中定义了统一返回体：

- `Result<T>`：基础返回结构，包含 `code` 和 `msg`
- `ApiResult<T>`：在基础返回体上增加 `data`、`total`
- `PageResult<T>`：专门用于分页返回

### 3.1.1 `ApiResult` 的作用

`ApiResult` 提供了多种静态工厂方法，例如：

```java
ApiResult.success()
ApiResult.success(data)
ApiResult.success(data, total)
ApiResult.success("登录成功", map)
ApiResult.error("密码错误")
```

它的价值在于：

1. **统一接口返回格式**，前端处理更简单；
2. **减少重复代码**，Service 层只需关注业务；
3. **分页与非分页复用同一套响应体系**。

### 3.1.2 `PageResult` 的作用

分页接口通常返回两类信息：

- 当前页数据列表
- 满足条件的总记录数

因此 `PageResult.success(data, total)` 适合用于列表查询场景，例如：

- 用户查询
- 商品查询
- 订单查询
- 评论查询
- 消息查询
- 操作日志查询

---
### 3.2.1 Token 生成

`JwtUtil.toToken(id, role)` 负责创建 token，并把以下信息写入 token：

- 用户 ID
- 用户角色
- 过期时间（7 天）
- 唯一随机 ID

生成 token 后，登录接口返回给前端保存。后续请求时，前端在请求头中携带 `token`。

### 3.2.2 Token 解析

`JwtUtil.fromToken(token)` 用于解析 token：

- 解析成功：返回 `Claims`
- 解析失败：返回 `null`

这样可以在拦截器和权限切面中快速判断用户是否登录、身份是否合法。

---
## 3.3 ThreadLocal 保存当前用户

项目定义了 `LocalThreadHolder`：

```java
private static final ThreadLocal<Map<String, Integer>> USER_HOLDER = new ThreadLocal<>();
```

它的作用是：

1. 从 token 中解析出用户信息后，存入当前线程；
2. 业务代码中可以随时通过 `LocalThreadHolder.getUserId()` 获取当前登录用户；
3. 请求结束后通过 `clear()` 释放资源，避免内存泄漏。

### 3.3.1 为什么要这样设计

在一次请求内，Controller、Service、AOP 切面都可能需要当前用户信息。  
如果每一层都重复解析 token，会增加代码冗余和开销。  
通过 ThreadLocal 存储身份信息，可以让后续业务层直接读取，结构更清晰。

---

## 3.4 请求拦截器 `JwtInterceptor`

`JwtInterceptor` 是系统的第一道认证防线。

### 3.4.1 核心逻辑

拦截器在请求进入 Controller 之前执行：

1. 放行 `OPTIONS` 预检请求；
2. 放行登录、注册、文件访问等无需认证接口；
3. 从请求头读取 `token`；
4. 调用 `JwtUtil.fromToken(token)` 校验 token；
5. 校验失败则直接返回“身份认证异常，请先登录”；
6. 校验成功后，把 `userId`、`roleId` 存入 `LocalThreadHolder`。

### 3.4.2 设计意义

这个拦截器解决了两个问题：

- **统一登录校验**：避免每个接口重复写 token 判断；
- **统一身份注入**：后续业务层可直接获得当前用户信息。

---

## 3.5 权限控制切面 `ProtectorAspect`

`@Protector` 注解用于接口级权限保护，例如：

- `@Protector(role = "管理员")`
- `@Protector`（只校验登录，不校验角色）

### 3.5.1 工作流程

`ProtectorAspect.auth()` 的执行过程如下：

1. 从当前请求中获取 token；
2. 解析 token，得到用户 ID 和角色；
3. 读取目标方法上的 `@Protector` 注解；
4. 如果注解设置了角色，则比较当前用户角色是否匹配；
5. 不匹配则直接返回“无操作权限”；
6. 匹配则将身份信息写入 `LocalThreadHolder`，继续执行目标方法；
7. 方法结束后清理 ThreadLocal。

### 3.5.2 典型应用场景

- 商品分类删除
- 用户后台批量删除
- 操作日志删除
- 后台用户修改
- 其他管理员功能

这种写法把“权限判断”从业务逻辑中抽离出来，提高了可维护性。

---

## 3.6 分页切面 `PagerAspect`

`@Pager` 注解用于分页参数自动转换。

### 3.6.1 核心逻辑

`PagerAspect.handlePageableParams()` 会检查方法参数中是否存在 `QueryDto`：

- 如果存在，则把前端传来的页码转换成 SQL 偏移量；
- 转换公式为：

```java
(current - 1) * size
```

例如：

- 前端传 `current = 1, size = 10`
- 转换后 SQL 偏移量为 `0`
- 前端传 `current = 3, size = 10`
- 转换后 SQL 偏移量为 `20`

### 3.6.2 作用

前端通常习惯从第 1 页开始计数，而数据库分页通常需要 `offset`。  
AOP 将两种分页习惯做了统一转换，避免每个查询接口重复手动处理。

---

## 3.7 操作日志切面 `LogAspect`

`@Log` 注解用于记录关键业务操作。

### 3.7.1 工作方式

当接口被 `@Log(detail = "...")` 标注后，`LogAspect` 会：

1. 在目标方法执行前构造 `OperationLog`；
2. 填充：
    - 操作详情
    - 当前用户 ID
    - 创建时间
3. 先写入数据库；
4. 再执行原方法。

### 3.7.2 作用

- 方便管理员回溯关键操作；
- 便于排查问题；
- 支持系统审计需求。

## 4. 用户模块核心代码分析
用户模块是系统入口，负责注册、登录、身份认证和个人信息维护。

---

### 4.1 用户登录接口设计（Controller 层）

`UserController.login()` 接收 `UserLoginDTO`，调用 `userService.login()` 返回结果。

典型接口职责：

- 接收账号和密码；
- 不直接写业务判断；
- 只负责转发到 Service 层处理。

### 4.2 用户登录业务逻辑（Service 层）

`UserServiceImpl.login()` 的核心逻辑如下：

1. 根据账号查询用户是否存在；
2. 若用户不存在，返回“账号不存在”；
3. 比对密码是否一致；
4. 检查账户是否处于异常登录状态；
5. 生成 JWT token；
6. 将 token 和角色返回给前端；
7. 更新最后登录时间。

#### 4.2.1 关键业务点

- **账号唯一性**：注册时先判断账号是否已存在。
- **密码校验**：登录时校验明文密码是否匹配（当前实现未体现加密，课程项目中可作为说明点）。
- **Token 生成**：登录成功后下发 token，后续请求统一认证。
- **登录时间记录**：便于展示活跃信息或审计。

---
### 4.3 用户注册逻辑

`UserServiceImpl.register()` 的逻辑：

1. 根据 `userAccount` 检查账号是否存在；
2. 若存在，返回“账号不可用”；
3. 组装 `User` 实体；
4. 设置默认角色为普通用户；
5. 设置初始登录状态和禁言状态；
6. 写入数据库。

#### 4.3.1 默认值设计

注册成功后自动补充以下字段：

- `userRole = USER`
- `isLogin = 可登录`
- `isWord = 可用`
- `createTime = 当前时间`

这保证了新用户数据完整，减少前端传参负担。

---

### 4.4 用户身份认证接口

`UserServiceImpl.auth()` 的作用是：

- 从 `LocalThreadHolder` 读取当前用户 ID；
- 查询数据库中的用户信息；
- 拷贝到 `UserVO`；
- 返回给前端。

这个接口常用于：

- 页面刷新后恢复登录状态；
- 获取当前用户头像、昵称、角色等信息；
- 验证 token 是否仍有效。

---
### 4.5 修改密码逻辑

`updatePwd()` 的设计较完整，体现了典型的密码修改校验流程：

1. 校验原密码、新密码、确认密码是否为空；
2. 判断两次输入的新密码是否一致；
3. 读取当前用户数据；
4. 校验原密码是否匹配；
5. 将新密码写入数据库。

这一段体现了后端对敏感操作的基本保护思路。

---

### 4.6 后台用户管理

用户模块还提供了管理员功能：

- `backUpdate()`：后台修改用户信息
- `batchDelete()`：批量删除用户
- `query()`：分页查询用户列表
- `getById()`：按 ID 查询用户

其中 `query()` 由 `@Pager` 和 `@Protector(role = "管理员")` 双重控制，说明该接口同时要求：

- 登录认证通过；
- 角色必须是管理员；
- 分页参数自动转换。

## 5. 商品模块核心代码分析
商品模块是平台最核心的业务模块之一，承担商品发布、编辑、查询、统计等任务。

### 5.1 商品发布与修改

典型流程：

- `save(Product product)`：新增商品；
- `update(Product product)`：更新商品信息；
- `batchDelete(List<Integer> ids)`：批量删除商品。

在 Controller 层中，接口通常只负责转发，请求进入 Service 后才处理具体字段。

### 5.2 商品查询

`ProductServiceImpl.query()` 对应商品列表查询，返回 `ProductVO` 列表并附带总数，适合前端分页展示。

查询参数一般由 `ProductQueryDto` 承载，可以按以下维度筛选：

- 商品名称
- 分类
- 所属用户
- 发布时间
- 状态等

### 5.3 商品下单逻辑 `buyProduct`

这是商品模块中最重要的业务之一，逻辑大致如下：

1. 根据商品查询条件获取商品详情；
2. 判断商品是否存在；
3. 校验库存是否足够；
4. 组装订单信息；
5. 保存订单；
6. 扣减商品库存；
7. 返回“下单成功”。

#### 5.3.1 关键细节

- **库存检查**：防止超卖；
- **订单构造**：下单前自动填充订单号、买家 ID、价格、创建时间；
- **库存扣减**：订单写入成功后同步更新商品库存。

### 5.4 订单相关辅助接口

商品模块还提供：

- `placeAnOrder(ordersId)`：将订单置为已下单/已交易状态；
- `refund(ordersId)`：标记订单进入退款流程；
- `queryProductInfo(ProductQueryDto)`：统计某个用户商品的互动情况。

### 5.5 商品互动统计

`queryProductInfo()` 会统计当前用户商品的三类互动：

- 浏览数
- 收藏数
- 想要数

实现方式是：

1. 先查出该用户的所有商品 ID；
2. 再查询这些商品对应的互动记录；
3. 按互动类型分类计数；
4. 返回 `ChartVO` 列表给前端图表使用。

这使后台可以展示“商品热度”和“用户活跃度”图表。
